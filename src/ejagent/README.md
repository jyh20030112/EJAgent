# EJAgent module guide

[中文](README_zh-CN.md) · [Project overview](../../README.md)

EJAgent is an agent harness: it prepares tasks, orchestrates execution and
evaluation, builds model context, and commits conversation state. The application
using EJAgent owns its environment, credentials, tools, and acceptance capabilities

## Choose and configure modules

| Module                                       | Configuration and application responsibilities                     |
| -------------------------------------------- | ------------------------------------------------------------------ |
| [Harness](harness/README.md)                 | Assembly, completion policy, Run limits, controls, lifecycle       |

| [Planning](planning/README.md)               | Capability catalog, task generation, plan updates, output recovery |

## Minimum application setup

`AgentHarness` requires `agent_id`, a `ModelPort`, and a `ToolExecutor`. Built-in
providers and `FunctionToolExecutor()` satisfy the last two interfaces; an empty
executor enables a text-only workflow. Persistence, planning, evaluation, skills,
and compaction are optional and require explicit assembly.

For evaluated tasks, register evidence sources and verification functions, then
bind their names in an `EvaluationPlan`. Dynamic planning additionally requires a
`VerificationCapability` catalog. These are application-defined capabilities;
evidence values are observed during execution, and task-specific plans can be
generated by the Planner. No new source or verifier implementation is generated
automatically from a user's query.

## Configuration boundaries

Each module documents constructor defaults, scope, prerequisites, and failure
behavior. Actor Run limits, Planner/Judge budgets, and completion retries are
separate controls. Result enums such as `RunStatus` describe outcomes, rather that.
switching features on. Internal constants are not public configuration options.

For console logging, [logger.py](logger.py) exposes
`setup_logger(name="ejagent", level="INFO", fmt=...)`; the default format is
`%(asctime)s | %(levelname)-8s | %(name)s | %(message)s`.
Existing handlers are retained, so subsequent calls do not replace their format

See the [usage guide](../../docs/usage-guide.md) for complete integration recipes
and [structured output guide](../../docs/structured-output.md) for JSON validation.
